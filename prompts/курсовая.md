# Курсовая работа (тип `курсовая`)

Используется вместе с `00_общие_правила.md`.

## Что это за документ

Пояснительная записка к курсовой работе или курсовому проекту по дисциплине. Показывает, что
студент умеет самостоятельно проанализировать задачу, спроектировать и реализовать решение,
обосновать выбор и оценить результат. Оформляется по ГОСТ 7.32-2017; структуру и обязательные
разделы задаёт методичка кафедры — она важнее этого промпта.

Обычный объём — 25–40 страниц основного текста без приложений (уточни по методичке).
Источников — не меньше 10–15, в том числе стандарты и документация используемых технологий.

## Шапка

```yaml
---
тип: курсовая
вуз: Полное название университета
факультет:
кафедра: Название кафедры без слова «кафедра» и без кавычек
город: Город
дисциплина: Название дисциплины
тема: Тема курсовой работы
студент: Фамилия И. О.
группа: Номер группы
руководитель: Фамилия И. О.
должность_руководителя: доцент, канд. техн. наук

листы: [задание]
направление: 09.03.04 Программная инженерия
заведующий: Фамилия И. О.
исходные_данные: |
  Первая строка исходных данных.
  Вторая строка исходных данных.
разделы_записки:
  - Введение
  - 1 Анализ предметной области
  - Заключение
  - Список использованных источников
графический_материал: Перечень схем одной строкой
дата_выдачи: «___» ____________ 2026 г.
срок_сдачи: «___» ____________ 2026 г.
---
```

- Обязательные поля титульного листа: `вуз`, `кафедра`, `дисциплина`, `тема`, `студент`,
  `группа`, `руководитель`, `город`. Год подставляется текущий.
- `вид_работы: КУРСОВОЙ ПРОЕКТ` — если это проект, а не работа.
- Лист задания (`листы: [задание]`) — если методичка требует задание в составе записки.
  `разделы_записки` должны совпадать с реальными разделами работы.
- Неизвестные персональные поля оставь пустыми и перечисли их пользователю.

## Структура

```markdown
# ВВЕДЕНИЕ
# 1 <АНАЛИТИЧЕСКИЙ РАЗДЕЛ>
## 1.1 …
# 2 <ПРОЕКТНЫЙ РАЗДЕЛ>
# 3 <РЕАЛИЗАЦИЯ И ПРОВЕРКА>
# ЗАКЛЮЧЕНИЕ
# СПИСОК ИСПОЛЬЗОВАННЫХ ИСТОЧНИКОВ
# ПРИЛОЖЕНИЕ А. <Название>
```

Программа проверяет наличие и порядок: ВВЕДЕНИЕ → разделы с номером → ЗАКЛЮЧЕНИЕ → СПИСОК
ИСПОЛЬЗОВАННЫХ ИСТОЧНИКОВ (допустимо «БИБЛИОГРАФИЧЕСКИЙ СПИСОК», «СПИСОК ЛИТЕРАТУРЫ») →
приложения (необязательны). Титульный лист, задание и содержание вставляются автоматически.

**Введение** (1,5–2 страницы): актуальность темы с аргументами; краткое состояние вопроса;
цель — одна, формулируется как результат («спроектировать и реализовать…»); задачи — список
из 4–7 пунктов, по которым построены разделы; объект и предмет (если требует методичка);
применённые методы и средства.

**Аналитический раздел:** описание предметной области, бизнес-процессы, требования, обзор
аналогов или методов со сравнительной таблицей и выводом.

**Проектный раздел:** модели и схемы (функциональная структура, диаграммы потоков данных,
модели данных, архитектура), обоснование решений и выбора средств — со сравнением
альтернатив по критериям, а не «потому что популярно».

**Реализация и проверка:** ключевые фрагменты кода с пояснениями, примеры работы, тестирование,
контрольный пример с ручным расчётом, результаты в таблицах.

**Заключение** (1–2 страницы): по каждой задаче из введения — что сделано и с каким
результатом; оценка ограничений и направления развития. Без новых фактов, которых нет в работе.

**Приложения:** полные листинги, исходные данные, большие таблицы результатов, руководство
пользователя. Каждое приложение упоминается в тексте.

## Особенности работ по базам данных

Если курсовая по проектированию БД (типичная структура методичек):

- анализ предметной области: бизнес-процессы, деловой регламент (правила и ограничения),
  требования к системе — нумерованным списком вопросов, на которые отвечают запросы;
- концептуальная модель «сущность — связь»: таблицы характеристик сущностей (сильная/слабая,
  идентификатор), атрибутов (простой/составной, однозначный/многозначный, производный),
  связей (мощность, обязательность); анализ ловушек разветвления и разрыва;
- логическая модель: ключи, правила перехода, нормализация до 3НФ/НФБК с примерами
  аномалий, меры целостности (NOT NULL, CHECK, PRIMARY/FOREIGN KEY с действиями ON DELETE);
- выбор СУБД — сравнительная таблица и метод (например, Парето);
- физическая модель: DDL, индексы, представления, обоснование денормализации, транзакции;
- SQL-запросы всех видов, которые требует методичка (простые, многотабличные, агрегаты,
  GROUP BY/HAVING, коррелированные и некоррелированные подзапросы, внешние соединения,
  самообъединение, DML) — каждый с назначением, текстом и **реальным** результатом выполнения;
- серверная часть (процедуры, функции, триггеры, представления) с демонстрацией работы и
  отказов при нарушении правил;
- приложения: исходные документы, макет данных, «запрос — ответ», полный код.

Имена таблиц и столбцов в тексте — с экранированием: `print\_order`.

Схемы для БД-курсовой (все в одном файле draw.io, по правилам раздела 4.8 общего промпта):

| Схема                                         | Лист                        | Содержание                                                                       |
|-----------------------------------------------|-----------------------------|----------------------------------------------------------------------------------|
| Функциональная структура                      | альбомный                   | подсистемы `1…n` и функции `n.m`                                                 |
| DFD по основным функциям (2–4 схемы)          | альбомный                   | процессы с номерами функций, сквозные хранилища D1…Dn, внешние сущности, легенда |
| Концептуальная модель ER                      | альбомный                   | 10–20 сущностей, связи с глаголами и кардинальностью, легенда                    |
| Логическая модель                             | книжный, несколько рисунков | таблицы с типами и ключами, по 5–9 таблиц на рисунок                             |
| Взаимодействие объектов серверного приложения | альбомный                   | вызовы процедур, операции над таблицами, срабатывание триггеров, легенда         |

Нотации — в разделе «Нотации схем» ниже.

## Нотации схем

| Схема                                          | Нотация и правила                                                                                                                                                                                                                                                                                                                                                                               |
|------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Функциональная структура                       | Дерево функций: корень — система, ниже — подсистемы с номерами `1`…`n`, листья — функции `n.m`. Эти номера наследуют процессы DFD                                                                                                                                                                                                                                                               |
| IDEF0                                          | Р 50.1.028-2001: блок — функция (глагол), номер `A0`, `A1`…; вход слева, управление сверху, выход справа, механизм снизу; контекстная диаграмма A-0 и декомпозиция на 3–6 блоков; все стрелки подписаны                                                                                                                                                                                         |
| DFD                                            | Гейн — Сарсон: процесс — скруглённый прямоугольник с номером функции (`4.3`); хранилище — открытый прямоугольник `D1…Dn` со **сквозной** нумерацией по всем DFD документа; внешняя сущность — прямоугольник с тенью; каждый поток подписан и начинается или заканчивается процессом (нет потоков хранилище→хранилище, сущность→хранилище); легенда: процесс, хранилище, внешняя сущность, поток |
| ER (концептуальная модель)                     | «Воронья лапка»: сущность — существительное в единственном числе; связь — глагол; на обоих концах линии — минимальная и максимальная кардинальность; M:N на концептуальной модели допустимо, штриховой линией; легенда: «ровно один», «ноль или один», «много», M:N                                                                                                                             |
| Логическая модель                              | Таблицы с колонками, типами, отметками PK/FK и NULL; линия ведёт от внешнего ключа к первичному; «воронья лапка» — со стороны дочерней таблицы; M:N уже разрешены ассоциативными таблицами; таблицы из других рисунков — «заглушками» со штриховой рамкой и ключевыми полями                                                                                                                    |
| Взаимодействие объектов (серверное приложение) | Пакеты и функции, таблицы — цилиндры, триггеры — шестиугольники; сплошная стрелка — вызов или операция над таблицей, штриховая — срабатывание триггера; легенда                                                                                                                                                                                                                                 |
| UML                                            | UML 2.5: диаграммы вариантов использования, классов, последовательности, деятельности, компонентов, развёртывания — по нотации стандарта                                                                                                                                                                                                                                                        |
| Блок-схема алгоритма                           | ГОСТ 19.701-90: терминатор «Начало/Конец», процесс — прямоугольник, решение — ромб с выходами «Да»/«Нет», ввод-вывод — параллелограмм; поток сверху вниз и слева направо, стрелки — только при отклонении от этого направления                                                                                                                                                                  |
| Архитектура (C4, развёртывание)                | Контейнеры и узлы с технологией в подписи, связи с протоколом; легенда                                                                                                                                                                                                                                                                                                                          |

Схемы документа **согласованы между собой**: функции структуры = процессы DFD; хранилища DFD =
сущности ER = таблицы логической модели; в тексте к DFD — таблица соответствия
«хранилище D1…Dn — таблицы БД».

## Проверка схем

- [ ] Каждая схема — в нотации из таблицы выше, с легендой.
- [ ] Функции структуры = процессы DFD; хранилища DFD = сущности ER = таблицы логической модели;
  таблица соответствия хранилищ есть в тексте.

## Журнал ошибок и замечаний (курсовая)

Правило ведения — как в разделе 8 общего промпта.

- **Симптом:** в задании «Разделы пояснительной записки» не совпадают с разделами работы.
  **Правило:** заполнять `разделы_записки` по фактическим заголовкам после написания работы.
- **Симптом:** задание не поместилось на одну страницу.
  **Правило:** исходные данные и перечень графического материала — кратко, 2–4 строки каждый.
- **Симптом:** номера разделов «1.», «2.» с точкой.
  **Правило:** по ГОСТ 7.32-2017 номер раздела без точки: `# 1 АНАЛИЗ ПРЕДМЕТНОЙ ОБЛАСТИ`.

- **Симптом:** на диаграммах потоков данных одно хранилище называется D1 на одной схеме и D4 на
  другой; процессы пронумерованы 1, 2, 3 на каждой схеме заново.
  **Причина:** нумерация велась отдельно для каждой схемы.
  **Правило:** хранилища данных нумеруются сквозь все DFD (D1…Dn, одно хранилище — один
  номер) и сводятся в таблицу соответствия «хранилище — таблицы БД»; номера процессов
  наследуют номер функции из функциональной структуры (функция 4.3 → процесс 4.3).
- **Симптом:** на DFD поток идёт от внешней сущности сразу в хранилище.
  **Причина:** нарушена нотация Гейна — Сарсона.
  **Правило:** каждый поток данных начинается или заканчивается процессом; каждый поток
  подписан.
- **Симптом:** функциональная структура, DFD и модели данных противоречат друг другу
  (функции нет на DFD, хранилищу не соответствует ни одна таблица).
  **Правило:** после правки любой схемы сверить согласованность по правилу из раздела
  «Нотации схем».
